# 授信模式设计与创新性对照

工银边贸智链第二阶段研发文档。编写：ClawsGO Science Agent，2026-11-09。

适用范围：以 Demo 2.0 的五批贯穿案例和模拟情景为基础，研究融资支持机制并确定 Demo 3.0 的开发范围。文中所有数值来自模型在给定假设下的计算，均为模拟结果，不是已观察到的融资效果，也不构成授信建议。涉及工商银行产品、监管规定和实务做法的判断，来源和核验程度见第三节及《01_研究记录_产品与制度.md》。

## 一、结论

1. 本案例需要的融资工具，工行现有产品已经具备。国内订单融资、小企业订单融资、国内保理、数字供应链融资、经营快贷，加上《流动资金贷款管理办法》规定的受托支付和回笼账户管理，覆盖了"凭订单采购""凭应收融资""循环周转""按合同用途付款"这几项功能。本项目不提出新的贷款产品。

2. Demo 2.0 的模拟批准把甲的总额度从20万元提到31万元，从第21日用到第120日。这一安排与需求的实际形态不匹配。第20日账期草案下，甲的借款只在第40、41日超过20万元，超出部分最多10.672万元；第42日乙支付第3批货款13.608万元后，超出部分归零。需要的是两天、有明确回款来源的过桥资金，2.0 承诺的是近百日的一般额度。

3. 据此，原定研究方向收窄为：**由联合台账识别"已形成、已验收的某批应收"能否覆盖"尚未启动的某批采购"，形成批次专项提款的方案说明和提款条件清单，供银行在现有产品内选择办理方式。** 平台给出资金需要、可核验的回款依据、额度区间与期限的形成过程、提款前须满足的条件和复核提示；准入、额度、定价、产品选择和审批由银行作出。

4. 同一组3969条第20日历史匹配情景下，批次专项安排（13.608万元，第21—50日可提，第62日到期）与一般额度提高（31万元至第120日）相比：
   - 第五批按原计划采购的比例为98.2%和100%；
   - 甲的平均利息为664.6元和667.8元，基本相同；
   - 银行为本组交易额外承诺的额度×天数，平均317万元·日和1089万元·日，少约71%；
   - 在下游持续拖欠的压力情景中，两者期末甲本金都是23.5万元，专项安排没有降低尾部敞口，还使3.5万元专项本金自第63日起逾期。

5. 专项安排解决不了还款来源尚未形成的缺口。原账期下约10.1%的匹配路径出现第五批采购顺延，这些路径中约79%的第4批在第40日前尚未验收，约33%的路径乙对甲付款晚于合同日。这些路径没有可核验的应收作还款依据，需要银行按企业整体经营情况判断一般流动资金额度。本文把这类情形划在专项机制之外。

6. 从整条交易链看，账期草案本身的代价最大。第三至第五批改为15日后，乙的资金需要P90从20万元降到13.06万元，甲的资金需要上升，链条合计平均利息从581元升到757元。草案把乙受额度约束的压力转给了甲，融资只是让这种转移可以执行。是否接受草案，应由甲乙结合价格补偿协商；平台把这一代价放在融资方案之前展示。

## 二、问题与主体

### 2.1 不同主体的借款资格与责任

| 主体 | 法律地位（按本例假设） | 在本机制中的角色 | 说明 |
| --- | --- | --- | --- |
| 参与边民 | 自然人 | 不是本机制的借款人 | 边民个人经营贷适用《个人贷款管理办法》，与本组交易的批次融资分开。边民的收购尾款是甲的应付义务，专项资金可用于支付该尾款 |
| 边民互助组 | 一般为备案组织，不具法人资格 | 不作借款人 | 地方文件显示互助组以备案为主；未检索到全国性规定 |
| 合作组织甲 | 假设为依法登记的农民专业合作社或企业法人 | 本例的借款人 | 承担向边民收购、向乙供货；向乙收取货款。实际应用中须核验主体资格 |
| 加工企业乙 | 企业法人 | 甲的付款方；也可能是借款人 | 乙对甲的应付货款是专项安排的还款来源，需要乙确认。乙自身也有一般流动资金需要 |
| 平台 | 信息服务 | 不放款、不归集资金、不作授信决定 | 银发〔2025〕77号第四条 |

甲、乙分别记账、分别借款、分别承担还款责任。模型中甲的专项额度只能由甲提款，乙的应付确认只证明还款来源，乙不因此对甲的借款承担保证责任，除非银行另行要求并经乙同意。

### 2.2 本案例中有明确机制的融资问题

以下问题都可以在 Demo 2.0 的逐日台账中定位到具体批次和日期。

| 问题 | 机制 | 本例数值（确定性基准） |
| --- | --- | --- |
| 多批次连续占款 | 甲在采购时预付边民3500元/吨及物流费，验收后付100元/吨尾款，乙在验收后按账期付款。前批货款未回，后批采购又要付款 | 原账期下甲借款峰值17.064万元 |
| 贸易与采购节奏错配 | 乙把第三至第五批账期从5日改为15日，第3批货款由第32日推到第42日，第五批采购在第40日 | 草案下甲资金需要峰值30.672万元，对照20万元额度待筹10.672万元 |
| 额度与经营节奏不匹配 | 20万元额度下第五批采购从第40日顺延到第42日，回款从第65日顺延到第68日 | 甲清偿日第44日→第54日 |
| 下游回款不确定 | 乙的回款取决于成品下游客户付款，乙付甲的能力随之变化 | 下游持续拖欠时第180日乙欠甲39.3万元（一般额度提高后） |
| 未到账回款不能支付现实支出 | 模型只用已到账现金和可提额度付款 | 第40日的采购不能用第42日才到账的第3批货款 |
| 真实交易资料分散 | 合同、验收、付款回执、乙的账期提议分属不同主体 | 2.0 已按证据状态区分 |

### 2.3 单纯提高额度解决不了的问题

1. **承诺期限与需求期限不一致。** 一般额度提高后，银行在第21至120日都要为这11万元承担提款可能；实际只需要第40、41两天。
2. **还款来源未形成的缺口。** 原账期下顺延的路径中，大多数是第4批在第40日前尚未验收。此时没有已形成的应收可对应，提额只能依靠企业整体信用。
3. **账期变化的成本在主体之间转移。** 提额让甲按草案执行，但甲多付利息、乙少付利息，链条合计利息上升。额度不回答这笔成本应由谁承担。
4. **下游违约的传导。** 下游持续拖欠时，乙无力付甲，甲借来的钱已经付给边民和物流。额度越大，可被这种传导占用的借款越多。
5. **用途控制。** 一般额度可用于甲的任何经营支出，与特定批次之间没有对应关系，贷后难以判断某笔回款应归还哪笔借款。

### 2.4 三个概念的区分

| 概念 | 本例含义 | 由谁确定 |
| --- | --- | --- |
| 经营资金需求 | 不设额度时维持采购日历所需的借款峰值，草案下30.672万元；或对照现有额度的待筹峰值10.672万元 | 模型计算 |
| 合理授信额度 | 银行按借款人经营规模、资金循环周期、自有资金和其他融资测算（流贷办法第六、十九条及附件）。本组交易只是甲经营的一部分 | 银行测算 |
| 银行实际批准额度 | 审批结果，可能低于前两者，也可能不批 | 银行审批 |

平台只计算第一项，并为第二项提供本组交易范围内的材料。P90资金峰值、待筹峰值和情景结果都不能代替银行的授信判断。

## 三、现有产品与制度能做什么

### 3.1 工行现有产品（官网页面，检索日期2026-11-09，具体以当地网点为准）

| 本例需要 | 可对应的工行产品 | 已具备的功能 | 适用边界 |
| --- | --- | --- | --- |
| 甲凭乙的订单采购第五批原料 | 国内订单融资、小企业订单融资 | 发货前融资用于采购原料、组织生产，以订单项下预期销货款为主要还款来源；一般为订单金额70%，最高100%，最长1年 | 订单须来自企业法人等；要求与购货方两年以上稳定供销关系、双方在工行开户。新建的互市交易关系可能不满足 |
| 甲凭已验收的第3批货款融资 | 国内保理（小企业）；应收账款质押贷款 | 应收账款转让或质押，最高可融到应收金额 | 应收须权属清晰、未被转让或质押；债务人限企业法人等 |
| 甲的一般周转 | 经营快贷、网贷通 | 额度循环、随借随还 | 额度由银行模型或抵押物确定 |
| 依托核心企业的链式融资 | 数字供应链融资（垂直链、数据链） | 应收或货权质押，平台推荐客户，线上办理 | 需要核心企业或合作平台 |
| 提款与具体付款对应 | 流动资金贷款受托支付（流贷办法第二十九至三十一条） | 核对收款方、金额与商务合同相符后付给交易对象 | 受托支付金额标准由银行约定 |
| 回款用于还款 | 回笼账户管理（第三十六条） | 指定回笼账户，关注资金进出 | 合同约定 |
| 异常时停止放款 | 第三十三条、第三十七条 | 信用下降、用款异常可增加放款条件、停止或中止放款；预警时提前收回 | 银行按合同执行 |

他行也有相近做法：桂林银行"惠边贷"对落地加工企业按30%自筹、70%银行融资定向支付；中国银行防城港分行按纳税收入30%核定信用额度；建设银行广西区分行线上"边民贷"直连互市平台订单数据建模。这些说明"按真实交易定额""定向支付""用平台数据授信"在银行业已有实践。

### 3.2 现有产品已能解决的问题

- 单张订单发货前的采购资金：订单融资。
- 已验收、已形成应收后的资金回笼：保理或应收账款质押。
- 用途控制：受托支付按合同付款。
- 回款还款：回笼账户。
- 用平台数据核额：数字供应链融资（数据链）、他行的平台直连产品。

### 3.3 Demo 2.0 数据能增加的可核验信息

银行审查一笔订单融资或保理时，通常看的是借款人与一个交易对手之间的单张合同。Demo 2.0 在同一笔业务中同时记录了甲、乙两本台账和五个批次，能够补充以下信息：

1. **缺口的成因和位置。** 缺口由乙的账期变更引起，出现在甲的第40、41日，对应第五批采购。
2. **可对应的还款来源。** 第3批已于第27日验收，乙应于第42日付甲13.608万元，早于专项到期日；第4批要到第39日才验收。
3. **时间先后。** 第五批采购日（第40日）早于第3批货款到账日（第42日），所以必须借入两日；不是用未到账回款付款。
4. **跨主体传导。** 乙的下游回款延迟会推迟乙付甲，进而影响甲的还款。台账能看到这条链上每个节点是否按期。
5. **证据状态。** 合同、验收、付款回执分别标注待核验、存在差异、已核验。

这些信息的真实性仍需银行独立核实（银发〔2025〕77号第八条）。平台提供的是整理好的、能逐项追溯的材料，减少的是收集和对照的工作量；实际减少多少，需要试点验证。

## 四、候选机制比较

| 编号 | 做法 | 对应现有产品 | 判断 |
| --- | --- | --- | --- |
| M0 | 维持原账期，不新增融资（模型 A0） | — | 链条利息最低；原账期下仍有约10%路径第五批顺延，且主要因第4批未验收 |
| M1 | 甲一般额度提至31万元，第21—120日（Demo 2.0 口径，A2） | 流动资金循环额度、经营快贷提额 | 能保证按计划采购；新增的11万元可提期为99日，确定性基准下实际超出20万元的只有2日；与现有产品相同，作对照 |
| M2 | 第五批专项提款安排（A3）：13.608万元只用于第五批采购及其成员尾款；第3批已验收、付款日早于专项到期日、提款当日乙对甲无逾期应付时才可提；第62日到期，日终回款优先归还 | 应收账款质押或保理＋受托支付；或订单融资 | 金融工具不新。新增的是由联合台账确定"哪笔已形成的应收对应哪笔待启动的采购"，并把提款条件与履约节点对应。**采用，作为 Demo 3.0 的模拟对象** |
| M3 | 第3批验收后即做保理，第27日取得13.608万元 | 国内保理 | 与现有产品完全相同。本例中与 M2 在经济上基本等价：利率相同时利息相近；按应收存续期（第27—42日）粗算，额外占用约13.608万元×15日＝204万元·日；M2 自第21日开放计至归还，确定性基准下约286万元·日，口径不同，只说明两者同一量级。差别是 M3 在验收时一次融资，M2 在需要时提款。银行办理 M2 时，保理是可选的现有产品形式之一（本项为手算估计，未纳入模型） |
| M4 | 维持原账期，乙一般额度提至30万元（A4） | 乙的流动资金贷款 | 乙的资金需要P90确实到了20万元上限，但提额后第五批按计划的比例只从89.9%升到91.2%，额外承诺990万元·日。原账期下的顺延主要不在乙 |
| M5 | 维持原账期，加第五批专项10万元，以第4批应收为来源（A5） | 同 M2 | 几乎不起作用：顺延的路径中第4批多数未验收，还款来源条件不满足，专项只在0.025%的路径被提用 |
| M6 | 第五批订单融资，以第5批应收（第63日）为还款来源 | 小企业订单融资 | 可办理，但还款来源晚于实际可用的第3批货款，额度占用期更长；第5批尚未发运，履约风险高于已验收的第3批 |

从比较看，候选方案的差别主要在**以哪一笔应收作还款依据、何时提款、承诺多久**。这些恰好是联合台账能回答的问题，单张合同看不出来。

### 5.2 额度建议的形成方式

平台不给出单一建议额度，只给出区间和每个取值在同一组情景下的表现，由银行决定。

- **下限：确定性待筹峰值 10.672万元。** 维持原采购日历所需借款超出现有额度的最大值。
- **上限：还款来源与用途的较小者。** 第3批乙付甲货款 36吨×3780元＝13.608万元；第五批采购支出 40吨×(3500＋100)元＋600元＝14.46万元，另有尾款0.4万元。取13.608万元，使专项本金不超过已形成的应收。
- **银行自行测算的合理额度**仍按流贷办法附件进行，本组交易只是甲经营的一部分。

| --- | --- | --- | --- | --- |
| 10.672 | 82.4% | 83.3% | 649.5 | 257.7 |
| 11.5 | 98.2% | 99.4% | 664.6 | 268.3 |
| 12.5 | 98.2% | 99.4% | 664.6 | 291.6 |
| 13.608 | 98.2% | 99.4% | 664.6 | 317.5 |

确定性下限在约16%的路径中不够用，因为验收和回款日期变动后，第40日前后的实际缺口会略高于确定性值。额度到11.5万元以后，按计划比例不再上升，剩下约1.8%的路径是因为第3批验收晚于第40日、还款来源条件不满足，再加额度也不会改变。演示默认填入上限13.608万元，客户经理可以改。

### 5.3 期限与提款安排

| 项目 | 本例取值 | 形成方式 |
| --- | --- | --- |
| 生效日 | 办理回执回填的下一日（第21日） | 与2.0 额度变更相同 |
| 提款截止日 | 第50日 | 第五批计划采购日＋10日 |
| 到期日 | 第62日 | 还款来源合同付款日（第42日）＋20日；不晚于一般额度到期日第120日 |
| 提款方式 | 不循环；累计提款不超过专项额度；只用于第五批采购及其尾款，尾款提用同样限于提款窗口内 | — |
| 提用顺序 | 先用现金，再用一般额度剩余空间，最后用专项 | 专项只补足差额 |
| 归还 | 日终回笼资金先还专项，再还一般额度 | 回笼账户约定 |

到期日的取舍：第62日到期时，基准12000条中0.017%、严峻6000条中0.083%的路径到期仍有专项余额，最大4.7万元；改为第90日到期后这两项为0。期限越长，技术性逾期越少，但银行发现问题的时点也越晚。演示默认第62日，并在页面中同时列出第90日的结果。

### 5.4 提款前须满足的条件

演示页面逐项显示以下条件。各项的执行方式不同，见列表后的说明：

1. Draft-V2 已由甲乙确认生效（账期变更是缺口的成因）。
2. 第3批验收记录已核验，且第3批合同付款日早于专项到期日。
3. 乙已确认第3批应付金额与付款日（工作流记录）。
4. 第五批采购单据已登记（受托支付对象与金额的依据）。
5. 提款当日乙对甲没有到期未付货款。
6. 甲没有欠息。
7. 在提款窗口内，且累计提款未达专项额度。

模型中，已承诺但未到账的回款不计入可用资金；第40日的采购只能用当日现金和可提额度支付。

第2、5、6、7项由引擎在每个提款日日初判定，不满足即不能动用专项。第1项通过专项的依据规则摘要执行：草案未生效前，获批专项不进入执行投影。第3项在审批时执行：乙未确认，客户经理不能记录批准。第4项只作展示，是受托支付核对收款方和金额的依据；演示中采购付款与单据登记分属不同环节，模型不以单据登记作为提款前提，真实办理时由银行在受托支付环节核对。条件5在本例中约束很弱：3969条匹配情景中从未因它受阻，因为第3批货款在第42日才到期，第40日提款时还谈不上逾期。我们比较过把条件扩到"乙的下游客户也没有到期未付"（S3）：下游持续拖欠的压力情景中它能在第40日拦下提款，甲期末本金为8.64万元，而不是23.5万元；但在正常情景中它也会拦下22.8%的匹配路径，第五批按计划比例降到77.2%，低于不融资的原账期。因此演示把下游逾期作为**复核提示**交给客户经理判断，不作为自动拦截条件。

### 5.5 复核提示与权限分工

平台在以下情况生成复核提示，由客户经理决定是否发起风险核查、暂停提款或要求补充材料。提示本身不改变额度、不改变借款状态：

| 触发 | 说明 |
| --- | --- |
| 还款来源到期未收 | 第3批合同付款日已过，乙对甲仍有未付差额 |
| 投影专项到期余额为正 | 按当前执行投影，专项到期日仍有本金未还 |
| 证据存在差异 | 与本专项相关的验收、付款或采购记录被标为"存在差异" |
| 下游回款逾期 | 乙的下游客户付款晚于合同日期，可能向乙付甲传导 |
| 采购未按计划启动 | 第五批采购日已过但尚未采购，可能是条件不满足或资金不足 |

| 主体 | 能做的 | 不能做的 |
| --- | --- | --- |
| 合作组织甲 | 提交专项方案说明；补充材料；登记采购单据 | 修改获批条件；作出银行结论 |
| 加工企业乙 | 确认第3批应付金额与付款日；确认账期草案 | 代甲申请；修改获批条件 |
| 客户经理（模拟） | 要求补件、批准或不批准；填写获批额度、窗口、到期日；回填回执；发起风险核查 | 代客户补件；在客户确认前改写合同 |
| 平台 | 计算、整理材料、逐项检查条件、生成提示 | 授信、定价、放款、归集资金、自动审批、自动提额、信用评分 |
| 成员 | 查看本人款项 | 查看他人或企业借款信息 |

### 5.6 实际推广需要的条件

1. 甲的主体资格：依法登记，能开立账户和签订借款合同。互助组不能作借款人。
2. 乙的配合：确认应付金额和付款日，同意银行核实；如采用保理或质押，须办理应收账款转让通知或在动产融资统一登记公示系统登记。
3. 银行产品口径：当地分行是否允许在一笔授信下设批次专项提款，或以订单融资、保理分笔办理；"两年以上供销关系"等准入条件能否满足。
4. 受托支付的对象：第五批收购款要付给众多边民，需要依托互市结算平台或代理结算账户，按批次核对名单和金额。
5. 数据授权：甲乙授权银行获取台账、合同、验收与回执；乙的下游回款信息需要乙授权。
6. 情景参数校准：当前的延误分布是演示假设，需要真实历史样本。
7. 定价：本例专项利率按4%年利率与一般额度相同，实际由银行定价。

## 七、与现有产品的对照：哪些重复，哪些是新增

### 7.1 与现有产品实质相同的部分（不作为创新点）

- 以订单或应收作还款来源的短期融资：订单融资、保理、应收账款质押。
- 按合同付款的用途控制：受托支付。
- 回款优先还款：回笼账户。
- 用交易数据或平台数据核额：数字供应链融资（数据链）；他行的互市平台直连产品。
- 信用下降时停止提款、提前收回：流贷办法第三十三、三十七条，银行合同的常规条款。
- 额度循环、随借随还：经营快贷等。

页面和文档中不用"智能授信""动态提额""AI风控"等名称描述上述功能。

### 7.2 本项目新增的部分

1. **跨主体缺口溯源。** 用同一笔业务的甲乙两本台账，说明甲的缺口来自乙的账期变更，出现在第40、41日，对应第五批采购。单张合同或单一主体的流水看不出这一点。
2. **还款来源与用款批次的配对。** 在五个批次中找出"已验收、付款日早于到期日"的应收（本例第3批），并区分出没有可对应应收的缺口（原账期下的顺延路径）。后者明确交回银行的一般授信判断。
3. **把提款条件写成可逐项核对的履约节点。** 条件对应的是联合台账里已有的事件：草案确认、第3批验收核验、乙的应付确认、第五批采购登记、当日无逾期应付。
4. **同一组情景下的安排对照。** 原额度、一般提额、专项、乙提额等安排在同一组历史匹配路径上比较按计划比例、利息、额外承诺和压力敞口，改善和代价同时列出，供客户经理参考。
5. **账期变更成本的显性化。** 融资方案之前先展示链条合计利息和主体之间的转移，避免把"多借钱"当成唯一出路。

这些都是信息整理和测算，没有一项是放款、定价或审批。它们能否减少银行核查工作、提高方案适配度，需要试点中与客户经理基于同一材料的判断对照（计划书6.4.2节已列的评价方法）。

### 7.3 收窄的范围

- 不提出新的贷款产品名称，也不声称工行已有或将有"批次专项额度"产品；银行可用订单融资、保理或流贷分笔办理。
- 不处理还款来源尚未形成的缺口。
- 不把下游逾期作为自动拦截条件。
- 不给出单一建议额度，不排序推荐方案。
- 不量化"风险下降""效率提升"的比例。

## 九、Demo 3.0 开发范围

论证结论支持开发，范围限于第五节的机制。功能并入现有"金融转译与核查"工作区，不新增导航页，八个工作区和 2.0 的贯穿案例保持不变。

| 功能 | 内容 | 实现层 |
| --- | --- | --- |
| 融资支持方案说明 | 在金融需求转译下方显示：缺口形态、可对应的还款来源批次、额度区间及其依据、期限与提款窗口、提款条件逐项状态 | `workflow.ts` 新增 `financingPlan()`；页面 |
| 安排对照 | 同一确定性路径下原额度、一般提额、专项三种安排的采购日、借款峰值、利息、清偿日、额外承诺；可在计算线程中对同一组历史匹配情景运行三种安排 | 引擎；`study.ts` 新增 `financingStudy()` |
| 结构选择与乙方确认 | 提交融资需求时可选"一般额度调整"（2.0 原流程）或"批次专项提款"；专项须先由乙确认第3批应付 | `submitBank`、新增 `confirmReceivable()` |
| 银行模拟审批 | 客户经理填写专项额度、提款截止日、到期日；系统校验额度不超过还款来源和用途上限、到期日晚于还款来源付款日且不晚于一般额度到期日、生效日晚于审批日 | `bankDecision` 扩展 |
| 按获批条件执行 | 回执回填后，专项自下一日写入执行投影；提款与归还生成证据记录（模拟） | `acknowledgeBank`、`evidenceSchedule` |
| 复核提示 | 5.5节所列情形逐项检查，客户经理可据此发起风险核查 | 新增 `reviewSignals()` |
| 前后对照 | 获批前（原额度）与获批后执行投影的采购、回款、清偿、借款对照 | 页面 |

防错要求（均写入流程检查）：同一草案不能重复提交融资；同一时间只能有一项生效的专项安排；审批前、生效日前不能提款；累计提款不超过专项额度；经营角色不能作出或修改银行条件；乙未确认应付时不能批准专项；未到账回款不能支付现实支出（引擎约束）；已发生的履约事实不被改写。

不开发：信用评分、自动审批、自动提额、额度推荐排序、真实银行或支付接口。

计算约束：2.0 的基准结果（17.064→30.672万元、待筹10.672万元、第五批第40→42日、回款第65→68日、清偿第44→54日）作为原有场景保留；专项安排是新的对照场景。新安排带来的变化全部由引擎计算，不在代码中写入结果。
