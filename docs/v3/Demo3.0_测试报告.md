### 3.2 浏览器计算线程情景统计（`scripts/check-financing-study.mjs`，129项）

用页面同一函数 `wf.arrangements()` 生成四种安排，经 `financingStudy()`（计算线程所用代码）在第20日匹配3969条、基准12000条、严峻6000条上计算，与 Python `financing_study.py` 的结果逐项比较（相对误差1e-6）。129项一致。

### 3.3 融资安排逐路径对照（`npm run test:financing-crosscheck`）

Python `export_financing_crosscheck.py` 导出11种安排 × 基准12000、严峻6000、确定性、持续拖欠，共44组；前端引擎逐路径重算。198022条路径、8514946项数值，最大绝对差0。

负对照：把 S1 安排的专项额度从106720元改为106719元，12000条基准路径中1417条的甲峰值或第五批采购日与 Python 不一致，说明对照能识别参数变化。

### 3.4 浏览器测试（`npm run test:e2e`，Edge 无头，对象为 `dist/`）

原有7项（八个工作区与外部请求、第20日2.0融资流程、零新增风险核查、计算线程12000条与3969条匹配、成员视图、手机390×844无横向溢出、`file://` 打开）全部通过，未改动。

新增3项（`e2e/financing.spec.ts`）：

1. `?scene=financing`：方案说明数值与条件状态；甲视图无应付确认按钮，乙确认后条件变为满足；提交专项；重复提交不新增事项，改为一般额度申请被拒；经营角色看不到银行条件输入；客户经理输入14万元被拒、到期日第40日被拒，改为13.608万元、第62日后批准；回填回执；甲确认草案后，执行对照显示第五批第42日→第40日、回款第68日→第65日、第40日提用10.672万元第42日归还、一般/合计峰值20.000/30.672万元；履约台账在第20日不显示未来的专项凭证，推进到第42日后显示提款与归还；留痕包含"应付确认""办理回执回填"。
2. 计算线程在3969条匹配情景中对照四种安排：按计划比例89.9%、0.0%、100.0%、98.2%；专项提用99.4%、受阻1.8%、额外承诺317万元·日。
3. `?scene=financing-stress`：办理专项后，复核提示给出"专项到期日第62日仍有本金3.500万元"和下游回款逾期；客户经理依据提示发起风险核查，获批专项记录不变。

## 五、开发中发现并修正的问题

- 页面走查发现专项可在提款窗口外用于成员尾款，改为与采购相同的窗口限制（TS 与 Python 同步修改后重跑全部对照）。
- "条件受阻日"最初在日初计数，会把用自有资金当日完成采购的情况算进去，改为当日最终仍未采购才计数。
- 根目录 `index.html` 不由构建脚本生成，3.0 首次提交时仍为 2.0 版本，已同步。
- 一项浏览器测试最初定位到错误的表格，是测试写法问题，修正后通过。
